§1

Object constructors

Manually typing out the contents of all of our objects with object literals is not always feasible. When you have a specific type of object you need to make multiple of, a better way is an object constructor — which is really just a function.

function Player(name, marker) {
  this.name = name;
  this.marker = marker;
  this.sayName = function() {
    console.log(this.name);
  };
}

const player1 = new Player("steve", "X");
const player2 = new Player("also steve", "O");

Lesson note — Safeguarding constructors

Since constructors can be called without new by mistake — which causes hard-to-track errors, as it won't do all the new-object and this-binding work — we should safeguard them. The new.target meta-property throws an error if Player is called without new:

function Player(name, marker) {
  if (!new.target) {
    throw Error("You must use the 'new' operator to call the constructor");
  }
  this.name = name;
  this.marker = marker;
}

Lesson note — console.log vs return

We use examples of functions that call console.log() for demonstration, but instead of making functions directly log things, it's generally more sensible to make them return values. That way you can pass the values wherever you wish without being tied to whatever that function does — you may not always want to log the value.

§2

The prototype

All objects in JavaScript can be linked to another object, called their prototype (also written [[Prototype]]). If a property or method is not found on the object itself, JavaScript looks for it in the [[Prototype]]. The lesson breaks this into three sentences:

#The sentenceWhat it means here
1All objects in JavaScript have a [[Prototype]]player1 and player2 both have one. Check it with Object.getPrototypeOf().
2The [[Prototype]] is another objectIt can have properties and functions, just like player1 does. Here it is the object at Player.prototype.
3…that the original object inherits from, and has access to all of its methods and propertiesAnything defined on Player.prototype is available to every Player object.
 
Object.getPrototypeOf(player1) === Player.prototype; // returns true
Object.getPrototypeOf(player2) === Player.prototype; // returns true

// defining a function 'on' the prototype
Player.prototype.sayHello = function() {
  console.log("Hello, I'm a player!");
};
player1.sayHello(); // logs "Hello, I'm a player!"
player2.sayHello(); // logs "Hello, I'm a player!"

Define sayHello once and both players can use it — you never touched either player object. That is the point of the prototype.

Lesson note — .__proto__

In some docs or codebases you may see .__proto__ used to get or set an object's [[Prototype]] instead of Object.getPrototypeOf() / Object.setPrototypeOf(). This is for historical reasons — .__proto__ is non-standard and deprecated, so it is not recommended.

Lesson note — Object.getPrototypeOf() vs .prototype

A common cause of confusion. .prototype is a property of functions that determines what a new instance's [[Prototype]] will be set to when the function is called with new.

.prototype is not for accessing an object's [[Prototype]] — that is what Object.getPrototypeOf() is for.

§3

Prototypal inheritance

What use is an object's [[Prototype]]? The lesson narrows it to two reasons:

#Reason
1To save memory. Defining every property and function on every object takes a lot of memory, especially with many common functions and many created objects. Defining them on a centralized, shared object saves memory.
2To share and reuse behaviour through JavaScript's prototypal inheritance mechanism — letting player1 and player2 access functions like .sayHello defined on Player.prototype.

hasOwnProperty — own vs inherited

How do we know .valueOf is defined on Object.prototype and not on player1? We use another function that itself comes from the chain:

player1.hasOwnProperty("valueOf");           // false
Object.prototype.hasOwnProperty("valueOf");  // true
Object.prototype.hasOwnProperty("hasOwnProperty"); // true

Two notes from the lesson

1. Every prototype object inherits from Object.prototype by default, whether directly or indirectly.

2. An object's Object.getPrototypeOf() value can only be one value — an object cannot have multiple [[Prototype]]s.

§4

Recommended method — do's and don'ts

Just as Object.getPrototypeOf() gets an object's prototype, Object.setPrototypeOf() sets it. It takes two arguments: the first is the one which inherits, the second is the one you want it to inherit from.

// ✅ DO — make Player.prototype INHERIT FROM Person.prototype
Object.setPrototypeOf(Player.prototype, Person.prototype);

// ❌ DON'T — this makes them the SAME OBJECT in memory
Player.prototype = Person.prototype;

Both Player.prototype and Person.prototype become the exact same object, so any change to one also changes the other. Watch it happen — the lesson's own Enemy example:

function Person(name) { this.name = name; }
Person.prototype.sayName = function() {
  console.log(`Hello, I'm ${this.name}!`);
};

function Player(name, marker) { /* … */ }
function Enemy(name) { /* … */ }

// the mode toggle below switches between:
//   Player.prototype = Person.prototype          ❌
//   Object.setPrototypeOf(Player.prototype, …)   ✅

Enemy.prototype.sayName = function() {
  console.log("HAHAHAHAHAHA");
};

const carl = new Player("carl", "X");
carl.sayName();

Don't — Player.prototype = Person.prototype

Both become the exact same object in memory. Any change made to Player.prototype also affects Person.prototype, which is not the intended behaviour. Instead, make Player.prototype inherit from Person.prototype, rather than making them the same object.

Do — but set the chain up before creating objects

Though Object.setPrototypeOf() seems an easy way to set up prototypal inheritance, the prototype chain has to be set up before creating any objects. Using setPrototypeOf() after objects have already been created can result in performance issues.

DigitalOcean

Understanding Prototypes and Inheritance in JavaScript

Odin's framing: "a good review of prototype inheritance and constructor functions, featuring some examples."

  • Its four sections: JavaScript Prototypes → Prototype Inheritance → Constructor Functions → Conclusion.
  • The lookup rule. JavaScript searches the object itself first, then its [[Prototype]], then that object's prototype, and so on until the end of the chain. At the end sits Object.prototype; searching beyond it gives null.
  • Chains have different lengths. A plain object is one link: x → Object. An array is two: y → Array → Object. You can verify with y.__proto__ === Array.prototype and y.__proto__.__proto__ === Object.prototype.
  • Constructor functions are just regular functions — a function becomes a constructor when it is called with new. By convention we capitalise the first letter.
  • Define properties in the constructor, methods on the prototype. The article states this is common practice in JavaScript, for efficiency and readability — its Hero(name, level) holds the data, Hero.prototype.greet holds the behaviour.
  • Chaining constructors with call(). Hero.call(this, name, level) copies the parent's own properties into a child constructor such as Warrior or Healer.
  • The catch worth remembering: call() copies properties but does not link prototypes. After only call(), hero1.greet() throws "is not a function". You must also run Object.setPrototypeOf(Warrior.prototype, Hero.prototype) — and put it before any additional prototype methods.
  • It uses __proto__ for demonstration but says plainly it is a legacy feature that should not be used in production code.
JavaScript.info

Prototypal Inheritance

Odin's framing: go "a bit deeper into both the chain and inheritance" — and do the exercises at the end. Don't skip them.

  • The core rule: when you read a property from an object and it is missing, JavaScript automatically takes it from the prototype.
  • Two limitations. (1) The references cannot form a circle — JavaScript throws if you try. (2) The value of [[Prototype]] must be either an object or null; any other type is ignored.
  • Writing does not use the prototype. This is the point most people miss. Assignment and deletion operate on the object itself, never the prototype. Reading walks the chain; writing does not.
  • The exception is accessor properties — a setter defined on the prototype does run, and it modifies the calling object.
  • The this rule, stated crisply: in a method call, this is always the object before the dot. A method may be inherited from a prototype, but when it runs, this is the object it was called on — not the prototype that stores it. This is why shared methods can safely modify per-object state.
  • Iteration differs. for..in loops over own and inherited enumerable properties. Object.keys(), Object.values() and friends only see the object's own properties. Use hasOwnProperty() to tell them apart.
  • ⚠️ Odin's own warning about this article: it makes heavy use of __proto__, which is not generally recommended. Read it for the concepts; you will soon learn better ways to set the prototype.

§7

Knowledge check

The lesson's six questions. You are not expected to memorize or master this knowledge.

How do you write an object constructor and instantiate the object?

Write it as an ordinary function, capitalised by convention, that assigns to this. Instantiate it by calling that function with new. function Player(name, marker) { this.name = name; this.marker = marker; } const player = new Player("steve", "X");

How can you prevent that an object constructor is called without using the keyword new?

Use the new.target meta-property to safeguard it. When the function is called without new, new.target is undefined, so you can throw. if (!new.target) { throw Error("You must use the 'new' operator to call the constructor"); }

What is a prototype and how can it be used?

A prototype ([[Prototype]]) is another object that an object is linked to and inherits from. If a property or method is not found on the object itself, JavaScript looks for it in the [[Prototype]]. You access it with Object.getPrototypeOf(). Define properties and functions on a constructor's .prototype and every object created from that constructor can use them — Player.prototype.sayHello = function() {…} makes sayHello available to both player1 and player2.

What is prototypal inheritance?

An object inherits from its [[Prototype]] object, which in turn inherits from its own [[Prototype]], and so on — forming a chain. JavaScript traverses that chain looking for a property or function. The chain does not go on forever: Object.getPrototypeOf(Object.prototype) is null, the end of the chain, and if the property was not found by then, undefined is returned. Two things to remember: every prototype object inherits from Object.prototype by default, and an object can only have one [[Prototype]].

What are the basic do's and don't's of prototypal inheritance?

DO use Object.setPrototypeOf(Player.prototype, Person.prototype) — the first argument inherits, the second is inherited from. DO set the chain up before creating any objects; doing it afterwards can cause performance issues.

DON'T write Player.prototype = Person.prototype. That makes them the exact same object in memory, so editing one edits the other — which is how carl.sayName() ends up logging "HAHAHAHAHAHA". DON'T use .__proto__; it is non-standard and deprecated.

How does this behave in different situations?

It depends entirely on how the function is called, not where it was written. In a method call it is the object before the dot. In a constructor call with new it is the newly created object. In a simple function call it is the global object — or undefined in strict mode. In an indirect call via call() or apply() it is whatever you pass. In an arrow function it is inherited from the enclosing scope, so arrow functions should not be used as methods. See §6 for all six with their pitfalls.

§9

Sticking points — the three that catch everyone

Come here after the quiz — especially if you missed Q7, Q12 or Q13. These three trip up almost every learner, and they are really one idea in three disguises: in JavaScript, objects link to each other — they do not copy each other. Everything below follows from that.

Quiz Q7

Why is the end of the chain null and not an object?

In plain words: the chain is a line of objects you can ask for help. Each one says "not me — ask the next one." null means there is no next one. It is a full stop, not another object.

Click each position to see what actually sits there:

  • ×Not Object — that is the constructor function. Functions and prototypes are different things.
  • ×Not {} — an empty object would mean there is still one more to ask, and the chain would never stop.
  • ✓null — the chain has to end somewhere, or a failed lookup would search forever. When the search runs off the end, you get undefined: "nobody had it."

Two different words, two different jobs: null is where the chain stops. undefined is the answer you get back when the search found nothing.

Quiz Q12

A method lives on the prototype — so why isn't this the prototype?

In plain words: think of a recipe pinned on a shared kitchen wall. The recipe says "add your flour." When Anna cooks, it means Anna's flour. When Ben cooks, Ben's flour. One recipe on the wall, but it always uses the flour of whoever is cooking.

The method is stored in one place. this is whoever called it. Those are two completely separate questions — and you already know the rule from the last lesson: look left of the dot.

Because this is the caller, one shared method can safely work on thousands of separate objects — which is the entire point of putting it on the prototype.

groundwork for Q13

What are call() and apply()?

In plain words: they are a way to run a function and choose what this will be. That is the whole idea. Everything else is detail.

The problem they solve

Imagine a short speech written on a card. It says:

“I am this.name”

The card is not about anybody yet. The blank gets filled in by whoever reads it out. In code, that card is just a function:

function introduce() {
  return "I am " + this.name;
}

Normally you get a this by putting the function inside an object and using a dot. But that means attaching it to every object that needs it. .call() lets you skip that: hand the card to someone and say “read this, as yourself”.

Who reads the card?

The function never moved, and nobody owns it. You just pointed it at a different object each time.

call vs apply — one tiny difference

When the function takes arguments, you have two ways to hand them over. The result is identical. Only the packaging differs:

greet.call (alice, "Hello", "!");    // arguments separated by COMMAS
greet.apply(alice, ["Hello", "!"]);  // arguments inside an ARRAY

// both give:  "Hello, I am Alice!"

How to remember it: Call = Commas.   Apply = Array.

Reach for apply when your arguments already sit in an array. Classic example: Math.max.apply(null, [3, 9, 4, 1]) gives 9, because Math.max wants separate arguments but you have an array.

A close relative — bind()

call and apply run the function right now. bind does not — it hands you back a new function with this permanently attached, to call whenever you like. That is the fix for the “storing a method in a variable loses the object” pitfall in §6, situation 3.

Why does call() not bring the methods along?

Step zero — what is call() even for?

The scenario is a text RPG. Every character has a name and a level. Warriors also have a weapon; Healers also have a spell.

Hero already knows how to set name and level. Warrior wants to reuse those two lines instead of retyping them. The only question is how. Try the four ways:

So in plain words: Hero.call(this, name, level) means “Hey Hero — do your setup work, but on my object, not a new one.”

That is all .call() ever does: run a function, and let you choose what this will be. You already met it in §6, situation 5 — this is that same tool doing a real job.

Now the actual sticking point

In plain words: Hero.call(this, ...) is a photocopy — it copies a few facts onto your form, once, and then it is over. Object.setPrototypeOf is a phone line — it lets you ring Hero whenever you need something you do not have.

Here is the real reason, and it is simpler than it looks. Remember the convention: properties go inside the constructor, methods go on the prototype.

function Hero(name, level) {
  this.name = name;     // ← INSIDE the function body
  this.level = level;   // ← INSIDE the function body
}
Hero.prototype.greet = function() { … };  // ← OUTSIDE it, added separately
✓ what call() runs
this.name = name;
this.level = level;
× what call() never sees
Hero.prototype.greet =
  function() { … };

call() does exactly one thing: it runs the function body. And greet was never in the function body — it was attached to Hero.prototype on a separate line. So call() cannot possibly have brought it. It never saw it.

The one sentence behind all three

JavaScript objects link, they do not copy. A link is live and shared, which is why one method serves every object (Q12) and why the links form a chain that must end somewhere (Q7). A copy is a one-time transfer of values, which is why call() gives you data but no behaviour (Q13).
